# QWEN CODE — PROJECT RULES

## 1. Project identity
This repository is Perfect Templates, a collection of premium, reusable website templates.
Each template is an independent subproject located inside `templates/`.

## 2. Current project
The first template is `templates/elora-ecommerce/`.
ÉLORA is a premium fashion and lifestyle e-commerce website.

## 3. Technology constraints
- HTML5
- CSS3
- Vanilla JavaScript (ES6+)
- No React, Angular, Vue or other frontend frameworks.
- No backend unless explicitly requested.
- No unnecessary dependencies or build tools.

## 4. Architecture rules
- Preserve the existing directory and file structure.
- Never recreate, rename, move or delete files without authorization.
- Keep HTML, CSS, JavaScript, images, icons and fonts in their designated folders.
- Keep code modular and reusable.
- Use relative paths correctly.
- Do not put all the project code into one HTML file.

## 5. Design standards
- Premium, modern, Apple-inspired visual quality.
- Clean layouts, elegant typography and consistent spacing.
- Responsive design: mobile, tablet and desktop.
- Smooth animations and meaningful micro-interactions.
- Consistent colors, buttons, cards and components.
- Prioritize usability, accessibility and performance.

## 6. Development rules
- Inspect the existing files before modifying anything.
- Work only on the requested task or phase.
- Do not skip requirements.
- Do not generate fake functionality.
- All visible interactive elements must work.
- Avoid duplicated code.
- Use semantic HTML and accessible controls.
- Keep CSS organized and JavaScript maintainable.
- Do not overwrite existing work without checking it first.

## 7. Quality assurance
After each phase:
- Check HTML structure and links.
- Check CSS and responsive behavior.
- Check JavaScript errors and interactions.
- Check image paths and missing assets.
- Report incomplete items and known limitations.

## 8. Communication and reporting
At the end of each phase, provide:
1. Tasks completed.
2. Files created or modified.
3. Features implemented.
4. Tests performed and results.
5. Remaining issues.
6. Recommended next phase.

Never claim that a task is complete if it has not been verified.

## 9. Strict execution rule
Do not start another phase without explicit user approval.
Do not change the architecture or technology stack on your own.
When an instruction is ambiguous, ask before making structural decisions.
